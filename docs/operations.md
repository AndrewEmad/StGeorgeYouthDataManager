# Deployment, recovery and verification

Both apps deploy from the root npm workspace. The API remains on .NET 8; ImageSharp is pinned to **3.1.5**. A local SDK 10 build does not establish .NET 10 application or hosting compatibility. No runtime upgrade is authorized until the exact-package gate has passed on the intended host. Credentials in appsettings are intentionally outside this remediation scope.

## Build and release

Run `dotnet test tests/YouthDataManager.IntegrationTests` with a local SQL Server or set `YDM_TEST_SQL_SERVER` to a server-only connection string. The harness creates and removes only its own random database. Run `npm ci`, `npm run test:utilities`, `npm run build`, and `npx playwright test --grep-invert "deployed app scopes"` in `5.FrontEnd`. Initial application bundles have a 500 kB error budget. Publish the API to a fresh versioned release directory rather than merging files from an older dependency set; keep the previous release for rollback. The GitHub Pages workflow performs frontend dependency installation/audit, shared utility tests, both client builds and browser tests, then publishes both apps together. It contains no backend job, tests, migrations, recovery operations or API publication; Pages deployment depends only on the frontend job.

Development clients target the local HTTPS API. Staging has a separate environment file: set its API URL to the actual staging host before deployment. Production preserves the configured existing API URL. Build configuration must be chosen explicitly; do not test production services with browser fixtures. `node e2e/package-pages.mjs <repository-name>` builds both clients using their real deployed base paths and checks manifests and Angular worker hashes. Custom domains/root hosting require the matching base paths rather than rewriting built files.

## Automatic startup migrations

The API automatically applies pending EF migrations and initializes missing roles/admin data before accepting requests in both development and production. `Database:InitializeOnStartup` defaults to **true** in every environment; no appsettings entry is required. Existing migration history makes subsequent starts apply only new migrations. Set `Database:InitializeOnStartup=false` (or `Database__InitializeOnStartup=false`) only when explicitly opting out, as isolated API tests do. Migration errors fail startup rather than serving an incompatible schema.

Obtain a database **and persistent-photo** backup before deploying an API version with schema changes. The API database account needs permission to apply its migrations. Optional reviewed scripts can be generated manually with `dotnet ef migrations script --idempotent --project 2.Infrastructure/YouthDataManager.Infrastructure --startup-project 4.WebApis/YouthDataManager.WebApi --output <reviewed-file.sql>`; avoid printing configuration or connection strings.

For legacy data, run `tools/schema-preflight.sql` before the first startup of the upgraded API. Resolve duplicate pending requests through audited withdrawal/supersession and correct oversized secondary phones with evidence. Startup applies all pending migrations, including `ReviewedLegacyConstraints`; unresolved legacy conflicts cause that migration to fail without silently truncating or deleting records. Optional staged deployment scripts can first apply additive migrations through `20261011115500_MeasuredAttendanceOwnershipIndex` when operators need a review period.

Run authenticated `POST /api/operations/backfill?dryRun=true&batchSize=100` first, inspect counts, then repeat bounded batches with `dryRun=false` until a new dry run reports zero. The operation is idempotent and records audits. Historical scheduled dates become PendingReview tasks; old positive attendance becomes finalized meetings with unknown eligibility. Review tasks and historical meeting rosters explicitly before enabling their KPIs. Full birth dates correct birthday months; no dates are invented for month-only birthdays and event timestamps are not shifted.

`ReviewedLegacyConstraints` fails before changing data if phones or pending duplicates still need review. The migration temporarily rebuilds the computed secondary-phone index while narrowing the validated base column. Coordinate API and clients after schema initialization. Retain compatibility endpoints during client rollout. Prefer a forward correction after release; rolling back note lengths to 1000 requires checking all stored notes first, and rolling back feature tables would destroy new workflow history.

## Database and photos

The “Data exports” screen produces reporting files. It is not a disaster-recovery backup. The old `/dashboard/backups` client URL redirects to it.

For SQL Server on the same Windows host, run `tools/Backup-Data.ps1 -Server <instance> -Database <database> -PhotoDirectory <persistent-upload-root> -BackupDirectory <backup-root>`. The SQL Server service must have access to the destination. The script makes a COPY_ONLY database backup with CHECKSUM and VERIFYONLY, copies every versioned photo, compares SHA-256 values and writes a manifest. Windows-integrated authentication is used. For a remote SQL host, use a server-visible database backup destination and transfer the verified backup into the bundle. Keep the bundle on a separate durable storage target with a retention policy and access appropriate for student data.

Versioned photos retain previous bytes when encoding or metadata persistence fails. Include the whole configured upload directory in the backup. Stop API writes and the notification worker during a coordinated backup where a strict shared recovery point is required. Never remove older image versions without verifying that retained database backups no longer reference them.

Restore the database into a **new isolated database name**, using RESTORE FILELISTONLY and MOVE for all logical files; restore photos into a separate directory. Check the bundle manifest and every photo hash, compare migration history and business row counts, and verify that each student/user PhotoPath resolves within the restored directory. Start a staging API against the restored connection and photo root, with notifications disabled, and test login, roster/task/approval histories, authorized photos, exports, readiness and representative image formats. Cut over only after the operator verifies the actual backup and host. Never restore over a live database as a validation step.

`dotnet run --project tools/YouthDataManager.RecoveryVerification` exercises real SQL BACKUP, VERIFYONLY, RESTORE/MOVE, restored student metadata and persistent-photo hashes/decoding against two random disposable databases. It retains evidence in `artifacts/restore-verification-*` and removes only its generated databases. This demonstrates the recovery mechanism locally; it does not certify production storage or a real production backup.

## Readiness and notifications

`/health/live` checks process availability. `/health/ready` checks database connectivity, pending migrations and writable/readable persistent-photo storage. Keep readiness unavailable during incomplete schema rollout. Authorized administrators can view `/dashboard/operations` and `/api/operations/metrics` for server errors, slow queries, worker lag and failed deliveries. Metrics use process counters and .NET meters; connect the hosting environment's collector for durable alerting. Restarting the process resets counters, while outbox deliveries/attempts/checkpoints remain in SQL.

Configure Firebase credentials, the two app navigation URLs, and a durable upload path on the actual host. Schedules and delivery claims persist in SQL; restart catch-up processes seven days per batch and advances the durable checkpoint until current; provider concurrency is bounded to four sends. `NotificationWorker:ProviderTimeoutSeconds` defaults to 15 seconds and is clamped to 5–30 seconds. Paused, deleted or edited schedules cancel obsolete queued occurrences before sending. Failed recipients are retried individually; invalid device registrations are removed, inactive users are skipped, and failed events remain visible. Retry failed notifications from the operations screen only after fixing the cause. A provider acceptance records “sent by provider”; it cannot prove device display or reading.

## Remaining release gates

Verify the actual IIS/container runtime, TLS, SQL permissions, upload volume persistence, FCM delivery/click navigation, both deployed worker scopes and manifests, PWA upgrade/recovery with drafts, production-like restore, and the deployment environment's resource limits. These require the real staging/hosting target. Browser fixtures intentionally isolate the UI from production and do not prove provider delivery. Keep .NET 8 until the separate .NET 10 gate passes ASP.NET/EF/Identity, authentication, isolated migrations and JPEG/PNG/WebP/GIF processing using ImageSharp 3.1.5 on that host.

## Reproducible browser and load verification

The Playwright server serves the real built clients while isolated API fixtures prevent production requests. Install Chromium, Firefox and WebKit with `npx playwright install`. Route and dialog suites traverse 320, 360, 390, 430, 768, 1024, 1440 and 1920px, landscape/text reflow, long Arabic/Latin content, keyboard focus and Axe contrast/labels. Visual tests use local fonts, fixed Cairo time and committed per-engine baselines. Loading/saving snapshots hold the API response pending until capture; do not regenerate baselines to hide a behavioral failure.

For the service-worker tests, run `node e2e/package-pages.mjs YouthDataManager --fixture-api=http://127.0.0.1:4173/__test/api`, then `npx playwright test pwa.spec.ts --workers 1`. Only staged test assets receive this loopback API and updated integrity hashes. Repackage with `node e2e/package-pages.mjs <repository-name>` before publishing; never publish the fixture package. API requests use `ngsw-bypass` to keep protected data out of the static offline cache.

Run `dotnet run --project tools/YouthDataManager.Benchmarks --configuration Release -- artifacts/benchmark-final.json` while browser/build work is stopped. Optionally set `YDM_BENCHMARK_SERVER` to a server-only isolated SQL connection. The tool creates/removes its own random database and records host/SQL metadata, plans, query counts and p50/p95/max results for 3,000 students, 50 servants, 100,000 calls, 25,000 visits and 104 weeks (317,200 roster entries). It tests twenty concurrent provider callers and twenty distinct authenticated ASP.NET clients, including mixed area/page filters and twenty distinct assignment-owner scopes. Targets are p95 <500ms for lists and <1000ms for reports. TestServer includes authorization, request handling and serialization; it excludes network/TLS/IIS latency and is not a production hosting certification.

Pages packaging verifies both builds in a fresh staging directory, then replaces the whole publication. Previous local publications are kept under ignored `artifacts/pages-previous-*` for rollback; no stale hashed files or fixture assets are merged into the new publication.

Microsoft .NET/EF/Identity dependencies remain on the compatible 8.0 line (8.0.31; [official release notes](https://github.com/dotnet/core/blob/main/release-notes/8.0/8.0.31/8.0.31.md)). The full NuGet vulnerability audit retains visible ImageSharp 3.1.5 advisories because the user explicitly requires that version. Upload limits/frame restriction reduce exposure; they do not resolve upstream vulnerabilities. Other audited backend and frontend dependency findings are remediated. See `remediation-checklist.md` for evidence and open deployment gates.

## Generated files and cleanup

`docs/verification-results.json` retains the completed local test, benchmark, audit and recovery results. Raw files under `artifacts/`, frontend `dist/`, `.angular/`, `pages/`, `playwright-report/`, `test-results/`, and .NET `bin/`/`obj/` are generated output and may be removed when no build or test is running. The commands above regenerate them. Old `node_modules.pre-workspace/` folders and `package-lock.pre-workspace.json` are obsolete migration backups; the canonical frontend workspace lock is `5.FrontEnd/package-lock.json`. Keep test sources, visual baselines, migrations, operational tools and the installed current workspace dependencies. Cleanup does not remove application configuration, credentials or persistent user photos.

Preview the checked allowlist with `./tools/Clear-GeneratedFiles.ps1 -WhatIf`; run `./tools/Clear-GeneratedFiles.ps1` locally to perform cleanup. The script validates workspace boundaries and tracked files, detaches only the three known obsolete dependency junctions without following them, and retains current dependencies. Automatic approval review rejected both the full cleanup and a single-report-folder deletion, so no generated folders have been removed by the agent.
